## 三個做錯了之後很難改的決定

### ① 單位獨立成表，而且**庫存單位**要選對

`products.stock_unit_id` 是這個品項的庫存記帳單位——所有進出貨都會換算成它。
茶論台斤、禮盒論盒。選錯了，之後盤點會很痛。

換算分兩層，函式 `product_unit_factor()` 自己判斷用哪一層：

| 情況 | 從哪裡來 | 例 |
| --- | --- | --- |
| 同量綱的物理換算 | `units.base_factor` 自動算 | 台斤 ↔ 兩 ↔ 公克 |
| 包裝換算 | `product_units` 的設定值 | 一包＝四兩、一盒＝2 包 |
| 兩者都不是 | **直接報錯** | 「包」沒設換算率就想扣庫存 |

第三條是刻意的：寧可開單當下失敗，也不要庫存悄悄算錯——年節對不上帳時，
你不會知道錯在三個月前的哪一筆。

### ② 庫存用異動記錄，不用數量欄位

`stock_moves.qty` 帶正負號，`base_qty` 是換算後的庫存單位數量（generated column，
資料庫自己算，前端不可能算錯）。現有庫存是 `sum(base_qty)`。

`factor` 是**當下**的換算率，寫死在那一列。日後包裝改了（一盒從 2 包變 3 包），
舊帳不會跟著變——這是異動記錄真正的價值，不只是「查得到誰改的」。

### ③ 訂單明細一律快照

`order_items` 存的是 `product_name` / `unit_name` / `unit_price` 的**當下值**，
不是即時 join 出來的。改價、改品名、品項下架，都不能動到已成立的舊單。

因為有這層快照，`product_prices` 就只需要存現行價，不必做價格版本表——
一天 5–10 單的規模，多一層歷史表只是負擔。

## 與架構文件的三處出入（要你點頭）

### 一、多了一張 `product_units`（第 6 張）

架構文件寫「核心九張表」。實際建出來是十一張：那份清單本身列了十張
（`orders` / `order_items` 算一組），我再多加一張 `product_units`。

為什麼非加不可：`units` 是**商家層級**的目錄，一台斤等於幾公克全街通用；
但「一盒等於幾包」是**品項層級**的包裝方式，同一家的不同品項答案就不一樣。
硬塞進 `units` 會得到一堆「A茶的盒」「B茶的盒」這種列；不獨立出來，
就只能把換算寫死在程式碼裡——那就違反了柱二「差異全部是資料」。

### 二、「四種業務型態」拆成三個軸

王老闆說的零售／禮盒／批發／宅配，其實不是同一個維度的四個值。混成一個
欄位以後一定會打架（「批發的禮盒要宅配」該填什麼？），所以拆開：

| 他說的 | 落在哪 |
| --- | --- |
| 零售 vs 批發 | `orders.price_tier_id`（價格層級） |
| 宅配 vs 自取 | `orders.delivery`（交貨方式） |
| 禮盒 | `products.category`（品項分類，不是訂單型態） |

### 三、月結／賒帳先不做

`orders` 只有 `is_paid` / `paid_at` 兩個欄位，記「收了沒」。真的有月結和
對帳單需求的話，那是一整塊應收帳款功能（額度、帳期、對帳單、沖帳），
**不該偷偷長在 orders 上**。這題王老闆一句話就能回答，見 `02-跟王老闆要什麼.md`。

## 資料隔離怎麼做到的

每張業務表都帶 `tenant_id` 並開 RLS。登入者能看到什麼，由這支函式決定：

```sql
current_tenant_ids()  -- 我在 members 裡屬於哪幾家
```

它是 `security definer`，自己不受 RLS 限制——否則查 `members` 會觸發
`members` 自己的政策而無限遞迴。這是多租戶 RLS 最常見的坑。

另外兩件已經做進去的事：

- **複合外鍵**。每張表都有 `unique (tenant_id, id)`，所有跨表參照都走
  `foreign key (tenant_id, xxx_id) references yyy (tenant_id, id)`。
  就算 RLS 全被繞過，A 家的訂單也**在資料庫層**不可能指到 B 家的品項。
- **`force row level security`**。連表的擁有者也受政策約束。

> ### ⛔ 一條鐵律
> **`service_role` key 只能放在伺服器端，永遠不准出現在前端或 LIFF 裡。**
> 那把鑰匙會繞過全部 RLS。前端一律用 anon key ＋ 使用者的 session。
> 這是這套系統唯一一個「一次疏忽就等於全街資料外洩」的地方。

LINE 的 channel secret 同理：`tenants` 只存 `line_secret_ref`（金鑰在 Supabase
Vault 裡的名字），**金鑰本身不落庫**。

## 驗證結果

`sql/004_smoke_test.sql`，在 PostgreSQL 16.13 實跑，七項全過：

| # | 驗什麼 | 結果 |
| --- | --- | --- |
| 1 | 單號每家每天各自從 001 起跳 | `20260825-001` ✅ |
| 2 | 訂單金額由明細自動加總（3 兩 × 250） | `750` ✅ |
| 3 | 庫存由異動加總，台斤／兩自動換算（進 10 台斤、出 3 兩） | `9.8125` ✅ |
| 4 | 包／盒的品項專屬換算（再賣 2 盒＝1 台斤） | `8.8125` ✅ |
| 5 | 沒設換算率 → 直接報錯，不會靜靜算錯 | 擋下 ✅ |
| 6 | B 家查 A 家的訂單／明細／客戶／品項／庫存 | 全部 0 列 ✅ |
| 7 | B 家想把資料寫進 A 家 | 被 RLS 擋下 ✅ |

測試跑完自動 rollback，不留資料。

> 這一輪測出過一個真的漏洞：`v_product_stock` 建成 security_invoker 之後，
> 忘了 `grant select` 給 `authenticated`，登入者查庫存會 permission denied。
> 已修在 `002_rls.sql`。**這就是為什麼要先跑一次測試再交出來。**
