# 回歸審查：這幾天的改動有沒有把原本會動的東西弄壞

審查日期：2026-08-11
範圍：`auto/` 底下 7 支被改過的腳本
判準：**不是找新功能的 bug，是找「修了 A 卻弄壞 B」的痕跡**

結論先講：**找到 4 個會壞掉的、3 個不一致、4 個可忽略。其中 2 個已用實際檔案／實際資料驗證過，不是推測。**
最嚴重的那個現在就已經生效 —— 產線下一支片（D4S1）發不出去，而且會把整條產線卡死。

## 🔴 會壞掉

### R1. 新加的文案檢查會擋掉 11／19 支排程，而且擋錯人 —— 產線會永久卡死

**檔案**：`desc_spec.py` 第 52 行 ＋ `publish_video.py` 第 17-26 行 ＋ `pipeline.py` 第 255-271 行
**嚴重度**：會壞掉（現在就已經生效，等 Veo 額度回來就會踩到）

實測結果（拿 `schedule.json` 真的跑一次 `desc_spec.check`）：

```
全排程 19 支，會被新檢查擋下：11 支
['d2s1', 'd4s1', 'd5s1', 'd6s1', 'd13s1', 'd14s1',
 'd15s1', 'd16s1', 'd17s1', 'd18s1', 'd19s1']
```

而 11 支裡面**只有 1 支（d2s1）是真的違規**，其他 10 支是誤殺。看被擋下的第 2 條長什麼樣：

| 影片 | 第 2 條開頭 | 判定 | 對不對 |
|---|---|---|---|
| d2s1 | `these are not butt prints. this is abstract art 🍫` | 擋 | ✅ 正確，這確實是第一人稱耍賴 |
| d4s1 | `An entire bag of flour has exploded across the living room and Taco is a walking white ghost…` | 擋 | ❌ **誤殺**，這是標準第三人稱劇情描述 |
| d5s1 | `The living room floor has turned into bubbling orange lava and Taco is stranded…` | 擋 | ❌ **誤殺** |
| d6s1 | `A big potted plant is face down on the floor and Taco is frantically shovelling…` | 擋 | ❌ **誤殺** |

原因就是第 52 行用**開頭字串比對**：

```python
THIRD_PERSON = ["Taco ", "The chihuahua", "the chihuahua", "The husky", "the husky"]
if not any(body.startswith(p) for p in THIRD_PERSON):
```

只要句子不是「Taco 開頭」就死。但英文寫劇情描述本來就常常先講場景再帶到主角
（`An entire bag of flour has exploded… and Taco is…`），這比 Taco 開頭還更符合規格書要的
「說清楚畫面發生什麼事」。同理會被誤殺的還有 `Taco's paws are…`（後面是撇號不是空格）、
`Taco, the chihuahua, …`（後面是逗號）、`Nova stares at…`（Nova 是哈士奇的名字，不在清單裡）。

**為什麼這是「改 A 壞 B」而不只是誤判**：連鎖反應在 `pipeline.py`。

1. `publish()` 呼叫 `publish_video.py` → 文案檢查不過 → `sys.exit(9)`
2. `publish()` 只看 `if ok and url`，把 exit 9 當成一般失敗 → log「發布失敗，下次再試」
3. 但 `state[key]` 裡 `approved=True, published=False` 沒有清掉，**也沒有失敗次數上限**（Veo 有 `VEO_MAX_FAILS`，發布沒有）
4. 下一次 tick 走到第 255-271 行那段 → 找到這支已核准未發布的 → 再發一次 → 再失敗 → **`return`**
5. 那個 `return` 在迴圈裡面，會直接結束整個 tick。**後面所有的生片工作永遠不會被執行。**

也就是：只要 D4S1 被核准，產線每 20 分鐘失敗一次、永遠不會前進，而且 D5S1 之後的片子一支都不會開始生。

**修法**（兩處都要改，只改一處不夠）：

`desc_spec.py` 把開頭比對換成「整句有沒有提到角色 ＋ 有沒有混進第一人稱」：

```python
NAMES = ("taco", "chihuahua", "husky", "nova")
FIRST_PERSON = (" i ", " i'm", " i've", " my ", " me ", " mine ")

def _third_person(body):
    low = " " + body.lower().replace(",", " ") + " "
    return any(n in low for n in NAMES) and not any(f in low for f in FIRST_PERSON)
```

驗證過：d2s1 照樣被擋（沒提到任何角色名），d4s1／d5s1／d6s1 全部放行。

`pipeline.py` 加發布失敗計數，避免任何理由的發布失敗把產線鎖死：

```python
    log("  發布失敗，下次再試")
    st["publish_fails"] = st.get("publish_fails", 0) + 1
    if st["publish_fails"] >= 3:
        st["approved"] = False
        st["awaiting_review"] = True
        log("  連續 3 次發不出去，退回待審，不再擋住後面的片子")
    state[key] = st
    save(STATE, state)
    return False
```

### R2. `--donor` 會把「深度圖」當成成品輸出 —— 已用實際檔案驗證

**檔案**：`gen_scene_local.py` 第 127-128 行（donor 分支的 SaveImage 節點 14）＋ 第 231-234 行
**嚴重度**：會壞掉（`--donor` ＋ `--out` 一起用時必定發生）

donor 分支比 depth 分支多插了一個 `SaveImage`（節點 14，存深度圖），於是這個 workflow 有**兩個** SaveImage。
而 `comfy_api.collect_images()` 是照 ComfyUI 執行完成的順序收檔案，`main()` 又直接拿 `imgs[0]`：

```python
print("saved", imgs[0])
shutil.copy(imgs[0], args.out)      # ← 複製到 --out 的可能是深度圖
```

節點 14 只依賴 DA3（11→12→13），節點 10 要等 KSampler 跑完，所以**深度圖一定先產出**。
ComfyUI 實際輸出的時間戳完全一致地證實了這件事，5 次 donor 執行沒有例外：

```
cn0.60_depth_00001_.png   14:04:33   ← 先
cn0.60_00001_.png         14:05:10   ← 後
wine_a_stain_depth        14:58:39   ← 先
wine_a_stain_00001_.png   14:59:13   ← 後
```

所以 `imgs[0]` 拿到的是那張 112 KB 的灰階深度圖，不是 1.4 MB 的成品。
`--out` 會被寫進一張灰灰的深度圖，而且它是張正常的 PNG，不會報錯 —— 靜默的錯。

（附帶證據：`we0.35_depth_00001_.png` 有深度圖卻沒有對應成品，那次是深度算完之後就掛了 ——
 就是 `make_depth.py` 開頭寫的那個 16 GB 爆記憶體。）

**修法**：`main()` 和 `sweep()` 不要用 `imgs[0]`，改成排除深度圖：

```python
final = [p for p in imgs if "_depth_" not in os.path.basename(p)] or imgs
```

或更乾脆：donor 分支的節點 14 從 `SaveImage` 改成 `PreviewImage`（要留檔就自己另存）。

### R3. `cmd_ok` 會提早最多 16 小時把片子發出去

**檔案**：`pipeline.py` 第 367-386 行（`cmd_ok`）對上第 262-267 行（`cmd_tick`）
**嚴重度**：會壞掉（發布時段整個失效）

`LEAD_HOURS = 16` 是新加的：片子提前 16 小時生好送審。
`cmd_tick` 很小心地處理了這件事 —— 已核准但還沒到時間就等：

```python
if not ready_to_publish(planned):
    log(f"✅ {k.upper()} 已核准，等 {planned:%m-%d %H:%M} 發布")
    return
```

但 `cmd_ok` 完全沒有這道檢查，賢賢一按核准就直接 `publish()`：

```python
item = next(...)
if item and ensure_edge():
    publish(key, item, st, state)      # ← 沒有 ready_to_publish(planned)
```

前一天 16:00 生好、賢賢晚上順手核准 → 隔天 08:00 的片子當晚就發出去了。
`SLOT_HOURS = {1: 8, 2: 20, 3: 0}` 這套時段安排等於沒有作用。這就是 LEAD_HOURS 從小改大之後沒有同步到的地方。

**修法**：`cmd_ok` 只標記核准，發布交給 tick：

```python
    item = next((i for i in sched["schedule"] if f"d{i['day']}s{i['slot']}" == key), None)
    if not item:
        return
    planned = slot_datetime(item["day"], item["slot"],
                            datetime.strptime(sched["day1_date"], "%Y-%m-%d"))
    if not ready_to_publish(planned):
        print(f"已核准，會在 {planned:%m-%d %H:%M} 自動發布")
        return
    if ensure_edge():
        publish(key, item, st, state)
```

### R4. `cmd_tick` 第 0 段的 `return` 會擋住所有生片工作

**檔案**：`pipeline.py` 第 257-271 行
**嚴重度**：會壞掉（跟 R1／R3 是同一條因果鏈的下游）

那個 for 迴圈裡不管走哪條路最後都是 `return`（等時間 → return；發布 → return）。
一旦有任何一支片卡在「已核准未發布」，整個 tick 就到此為止，
後面第 2、3 段的生場景圖／生影片一次都不會跑。

而「已核准未發布」現在有兩條路會發生：R1 的文案擋下（永久）、R3 修好之後的正常等待（最多 16 小時）。
兩種情況都會讓下一支片錯過它自己的 16 小時提前量 —— 正是 `LEAD_HOURS` 當初要解決的「08:00 才開工必定遲到」。

**修法**：等待的那條路改成 `continue`（或 `break` 出去繼續往下跑），只有真的動手發布時才 `return`：

```python
            if not ready_to_publish(planned):
                mins = (planned - datetime.now()).total_seconds() / 60
                log(f"✅ {k.upper()} 已核准，等 {planned:%m-%d %H:%M} 發布（還有 {mins:.0f} 分鐘）")
                continue          # ← 不要擋住後面的生片
```

### I1. `sweep()` 漏傳 5 個新參數，掃出來的最佳參數不能用

**檔案**：`gen_scene_local.py` 第 165-166 行
**嚴重度**：只是不一致（但會導出錯誤結論）

```python
wf = build(SWEEP_PROMPT, args.seed, w, s, tag,
           ckpt=args.ckpt, steps=args.steps, cfg=args.cfg)
```

`ref` / `depth` / `donor` / `cn_strength` / `cn_end` 五個全部沒傳 → 一律吃 `build()` 的預設值。
具體後果：

- `--ref taco_face.png` 被忽略，永遠用 `duo_full.png`。但程式自己的 `--ref` 說明寫著「雙狗圖會讓兩隻的特徵混成一團…要生兩隻狗就改用 taco_face.png」—— 掃描永遠在用那張已知會出問題的圖。

```python
        wf = build(SWEEP_PROMPT, args.seed, w, s, tag,
                   ckpt=args.ckpt, steps=args.steps, cfg=args.cfg,
                   ref=args.ref, donor=args.donor, depth=args.depth,
                   cn_strength=args.cn_strength, cn_end=args.cn_end)
```

（順帶：`imgs[0]` 那行也要套 R2 的修法，否則掃描結果表列出來的會是一排深度圖。）

### I2. depth 分支掉了 `ImageScale`，尺寸不合會被 ControlNet 硬吃

**檔案**：`gen_scene_local.py` 第 98-110 行（depth）對上第 111-138 行（donor）
**嚴重度**：只是不一致

先回答問的問題：**節點編號沒有衝突，也沒有殘留。** 兩條是 `if / elif`，互斥；
`depth` 用 13／16／17／20，`donor` 用 30／31／11／12／13／14／16／17／20，
基底 workflow 沒有這些編號，走 depth 時 DA3 那四顆（11/12/13/14）完全不會出現。這點是乾淨的。

真正的不對稱在別的地方：**donor 分支有節點 31 `ImageScale` 把圖縮到 `width × height`，depth 分支沒有。**
`--depth` 走的是 `LoadImage` 直接餵進 `ControlNetApplyAdvanced`，尺寸沒人管。
今天沒事是因為 `make_depth.py` 裡硬寫了 `W, H = 768, 1152` 剛好對得上；
只要有人手工做一張深度圖、或動了任一邊的尺寸，就會靜默不匹配。

另外節點 13 在兩條分支代表不同東西（depth 是 `LoadImage`、donor 是 `DA3Render`），
現在互斥所以安全，但哪天想同時支援兩者就會直接撞車。

**修法**：depth 分支補一顆 scale，順便把編號錯開：

```python
    if depth:
        wf["13"] = {"class_type": "LoadImage", "inputs": {"image": depth}}
        wf["15"] = {"class_type": "ImageScale",
                    "inputs": {"image": ["13", 0], "width": width, "height": height,
                               "upscale_method": "lanczos", "crop": "center"}}
        # …node 20 的 image 改成 ["15", 0]
```

## ⚪ 可忽略

### N1. `publish_video.py` 的 `--force` 位置放錯會炸，但不會靜默取錯檔

**檔案**：`publish_video.py` 第 10、17 行
**嚴重度**：可忽略（會壞但吵得很大聲）

```python
video, title_file, desc_file = sys.argv[1], sys.argv[2], sys.argv[3]
...
if "--force" not in sys.argv:
```

`--force` 是掃整個 `sys.argv`（位置無關），但三個檔名是硬取 1/2/3 號位。放錯位置的後果：

| 寫法 | 結果 |
|---|---|
| `publish_video.py v.mp4 t.txt d.txt --force` | ✅ 正常 |
| `publish_video.py --force v.mp4 t.txt d.txt` | ✗ `video="--force"` → Playwright 設檔案時報錯 |
| `publish_video.py v.mp4 --force t.txt d.txt` | ✗ `open("--force")` → FileNotFoundError |
| `publish_video.py v.mp4 t.txt --force d.txt` | ✗ 同上 |

**不會發生「發布到錯的影片」**，因為錯位一定是拿到 `--force` 這個不存在的檔名，開檔就死。
真正的問題只有錯誤訊息很誤導（看起來像檔案不見了）。`pipeline.py` 那條路永遠是正確順序、也不傳 `--force`，不受影響。

**修法**（一行）：

```python
args = [a for a in sys.argv[1:] if not a.startswith("--")]
video, title_file, desc_file = args[0], args[1], args[2]
```

### N2. `veo_backoff_h(out, 0)` 會取到最長的等待時間 —— 但目前叫不到

**檔案**：`pipeline.py` 第 113 行
**嚴重度**：可忽略（潛在，目前無法觸發）

```python
return VEO_BACKOFF_H[min(fails, len(VEO_BACKOFF_H)) - 1]
```

`fails=0` → `min(0,8)-1 = -1` → Python 負索引 → `VEO_BACKOFF_H[-1] = 2`（**最長的 2 小時**），
跟「前幾次快點重試」的設計意圖完全相反。

但唯一的呼叫點是第 334 行，前一行是 `fails = st.get("veo_fails", 0) + 1`，恆 ≥ 1；
全專案 grep 也沒有第二個呼叫點。所以**現在不會發生**，只是留了個地雷給未來（例如哪天有人想在生成前先問「下次要等多久」）。

`fails ≥ 1` 的行為都正確：1→0.1h、8→2h、9 以上照樣 clamp 在 2h，跟 `VEO_MAX_FAILS = 8` 對得上。

**修法**：`VEO_BACKOFF_H[max(0, min(fails, len(VEO_BACKOFF_H)) - 1)]`

### N3. 「額度用完」也在累加 `veo_fails`，八天後會自己停擺

**檔案**：`pipeline.py` 第 333-337 行
**嚴重度**：可忽略（慢性，八天才發作）

第 34-37 行的註解明講：「真正該等久的只有額度用完，那個走 `quota_reset_h()`」——
意思是額度用完不算服務失敗。但程式碼裡兩者共用同一個計數器：

```python
fails = st.get("veo_fails", 0) + 1
wait_h = veo_backoff_h(out, fails)      # 額度用完 → 走 quota_reset_h ✅
st["veo_fails"] = fails                 # ← 但次數照加 ❌
```

免費 Veo 每天會用完一次（`state.json` 裡 d4s1 已經 `veo_fails: 1`、d3s1 的備註也寫「免費額度已用完」），
每天加 1，第 8 天就撞到 `VEO_MAX_FAILS` → 「Veo 連續失敗 8 次，停止自動重試」——
但其實什麼都沒壞，只是排隊等額度。

**修法**：

```python
        quota = "額度用完" in out
        if not quota:
            st["veo_fails"] = fails
```

### N4. `browser_lock.release()` 會刪掉別人的鎖

**檔案**：`browser_lock.py` 第 44-48 行
**嚴重度**：可忽略（罕見，但一旦發生這個模組就等於不存在）

情境：A 拿著鎖但跑超過 30 分鐘（`STALE_MIN`）；B 判定過期、蓋掉鎖開始跑；
A 這時候才結束 → `atexit` 呼叫 `release()` → **把 B 的鎖刪掉** → C 立刻搶得到 → A 當初要防的「兩支同時操作 Edge」重新上演。
`run()` 給 `make_video_cloud.py` 的 timeout 是 1200 秒（20 分鐘），離 30 分鐘不算遠。

**修法**：刪之前先確認鎖是自己的：

```python
def release():
    try:
        if LOCK.exists() and f"pid={os.getpid()}" in LOCK.read_text(encoding="utf-8", errors="replace"):
            LOCK.unlink(missing_ok=True)
    except Exception:
        pass
```

另外：`publish_video.py` 是唯一一支操作遙控 Edge 卻沒有 `acquire()` 的腳本
（`make_scene` / `make_scene_ref` / `make_video_cloud` / `update_desc` / `veo_resume` 都有）。
它會 `page.goto` 並 `bring_to_front`，跟 `browser_lock.py` 開頭寫的規則不一致。不是今天的故障，但屬於同一類風險。
