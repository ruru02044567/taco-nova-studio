# LOCAL VIDEO ENGINE ROADMAP ＋ 九個問題的答案

> 建立：2026-08-16｜基準：**原版 TUF A16，RAM 16GB 單通道，未升級**
> 48GB / 4TB 是目標規格，本文件所有「現況」判斷都不採用它。

---

# 第一部分：九個問題

## 1️⃣ 原版 16GB RAM 能做到什麼？

**能穩定做到（`實測`）：**

| 能力 | 規格 | 成本 |
|---|---|---|
| Wan I2V 單段 5 秒 | 704×1280 → 拉到 1080×1920 | 6.5 分鐘/支 |
| 多鏡頭短片 | 每鏡各生場景圖分開跑再 concat，**絕不接龍** | 4 鏡 12 秒 ≒ 12 分鐘 |
| FLUX 生圖 | 1024×1024 / 832×1216 | 40–45 秒/張 |
| SDXL 生圖 ＋ ControlNet ＋ IP-Adapter ＋ 角色 LoRA | — | 未量測但已在用 |
| 靜態構圖與微動作鏡頭 | A 類 8/10 | 本機強項 |

**做不到或極不穩（`實測`）**：見問題 6。

**關鍵限制**：實測最低可用 RAM 掉到 **0.1–0.3 GB**。
16GB 這台是「剛好夠跑一件事」，不是「有餘裕」。同時跑生圖和生片會出事。

---

## 2️⃣ 目前最大瓶頸是 VRAM、RAM、模型能力還是 workflow？

**四個都是瓶頸，但各管不同的事——分開回答才有意義：**

| 你想改善的 | 真正的瓶頸 | 證據 |
|---|---|---|
| 穩定性（會不會 hang） | **RAM** | 實測最低剩 0.1 GB `實測` |
| 解析度上限 | **VRAM** | 6.00/8 GB，1080p 原生推測會 OOM `推論` |
| 動作品質、流暢度 | **模型能力** | 抖動 0.47 硬天花板，四種變數突破不了 `實測` |
| 控制精準度（要它做什麼就做什麼） | **workflow／缺元件** | Wan 側零控制元件 `實測` |

**如果只能挑一個答：模型能力。**

因為 RAM、VRAM、workflow 都是「花錢或花工可以改善」的，
但速度抖動 0.47 已經證明**四種變數（steps/shift/幀數/sampler）全試過都突破不了**，
而且「prompt 指定的動作根本不執行」是模型層現象，
社群對蒸餾版的抱怨與賢賢一字不差：「無視動作指令、生出 live wallpaper」。

**最容易被誤判的一點**：不要因為「RAM 快爆了」就以為升 RAM 能讓片子變好看。
那是兩件事。

---

## 3️⃣ Wan 是否仍值得保留？

**值得，但要縮小它的職責。**

**保留的理由：**
- A 類（靜態＋微動作）**8/10**，又快又免費，這一塊它做得好
- 頻道實測推翻了「本機畫質害死流量」：9,882 觀看那支是本機生的，198 觀看那支反而是純 Veo
- 它是目前**唯一**的本機影片模型，沒有替代品
- 全本機是賢賢已定的方向

**要改的是定位**：Wan 不是「動作片生成器」，是**靜態構圖與微動作的量產機**。
劇本要配合它的能力寫，而不是寫完劇本再要求它做到。

**不建議**：投入資源優化 prompt 去追動作幅度。已經證明是模型層限制，不是寫法問題。

---

## 4️⃣ I2V 是否比現在的 T2V 更值得發展？

**這題的前提要更正：現在用的就是 I2V，不是 T2V。**

`make_video_local_5s.py` 一定吃一張 `scene.jpg`，產線 100% 走 I2V。
T2V 這條路這個專案從來沒系統性測過。

**修正後回答：I2V 應該繼續當主力，T2V 不值得投資。**

理由：頻道的核心資產是 Taco 的固定外觀（黑點眉、藍項圈）。
**I2V 靠起始圖天然鎖住角色，T2V 先天做不到。**
而且現有的角色控制元件（IP-Adapter、ControlNet、taco/nova LoRA）**全部只能用在生圖階段**——
也就是說，起始圖那一步正好是目前唯一能鎖角色的一步，T2V 等於把它省掉。

T2V 只值得跑一組對照實驗（2 支）確認這個判斷有數據，然後就收手。

---

## 5️⃣ 哪一條本機 Video Engine 最值得下一步實作？

**排序如下：**

**第一名：AI Upscale 取代 lanczos**（BENCHMARK 的 B3）

- 現況：Wan 生 704×1280（90 萬像素），ffmpeg lanczos 拉到 1080×1920（207 萬像素）。**真實資訊量只有 43%**
- 成本最低：模型只有幾百 MB，比 Wan 小一個數量級
- **收益與模型能力無關**：就算 Wan 永遠學不會甩身，這條路一樣能讓片子看起來更清楚
- 風險最低：離線後製，不影響生成流程

**第二名：先跑 B1（1080×1920 原生能不能生）**
因為它決定第一名到底是「唯一路徑」還是「備案」。

**第三名：Wan 專用的 motion control（ControlNet 類）**
潛在收益最高——`MODEL_CAPABILITY.md` 明訂「加 ControlNet／LoRA」是死穴解禁條件之一。
但需要下載新模型，**等賢賢決定**。

**不建議現在做**：Video/Temporal Repair（零資產、VRAM/RAM 需求未知）、
非蒸餾版 Wan（每支 20–30 分鐘，這台跑不起量產）。

## 6️⃣ 哪些功能現在明確做不到？（`實測`，不是推測）

| 做不到的事 | 實際發生什麼 |
|---|---|
| 指定的小幅度動作（甩身、抖動） | 12 支全滅（6 種步數 × 3 顆 seed），一次都沒發生 |
| 受控的走路 | 不是不會走，是**不可控**——模型自己讓狗走向鏡頭，否定句完全無效 |
| 局部單肢動作（一隻爪子撥東西） | 會長出第三條腿 |
| 物件掉落／下沉 | 生出**反向浮起**，2.7 秒後融解成灰塊佔畫面 45% |
| 拿取／物件互動 | 道具第 2 秒憑空消失，手自己放下 |
| 多鏡頭接龍 | 第二段三次實測零例外全崩（長人手／增生第二隻狗／換品種） |
| 流暢度追上雲端 | 抖動卡死 0.47，四種變數都突破不了（Veo 0.191） |

## 7️⃣ 哪些只是尚未測試？（不要跟第 6 題混為一談）

| 未測項目 | 目前狀態 | 為什麼重要 |
|---|---|---|
| **1080×1920 原生生成** | 從沒測過 | 整個 benchmark 目標的前提 |
| **多角色同時動作** | 能力表 0 分是**推論**，從沒真的試過 | 所有成功案例的配角都是「睡著不動」 |
| **水／流體** | 從沒測過 | 「水」與「剛體掉落」未必是同一個死穴 |
| **微笑／奸詐微笑** | 從沒測過 | **這是頻道人設核心表情**，最該補的一格 |
| T2V vs I2V 對照 | 從沒系統性比較 | 見問題 4 |
| 非蒸餾版 Wan | 沒下載 | 蒸餾是動作弱的公認原因 |
| RAM 峰值（影片） | 腳本只量 VRAM 沒量 RAM | 這台真正的死因 |
| 雙通道記憶體頻寬收益 | 這台從沒在雙通道跑過 | 見問題 8 |

> ⚠️ **能力表上標「推論」的格子不是證據。** 跑步、跳躍、追逐、丟東西、複雜角色互動
> 這五項的 0–1 分都是**從已知死穴外推的**，只能拿來擋掉明顯做不到的事，
> 不可以講成「我們驗證過跑步不行」。

---

## 8️⃣ 升級到 48GB RAM 後最可能改善哪些項目？

**確定會改善（`推論`但有明確機制）：**

| 項目 | 為什麼會改善 |
|---|---|
| **穩定性 / 不再 hang** | 目前最低剩 0.1 GB，這是歷來死因。餘裕變大直接解掉 |
| **能同時跑生圖 ＋ 生片** | 現在只能一次做一件事 |
| **更大解析度的可行性提高** | 只在「VRAM 夠、需要 RAM 做 offload」的情境有效 |
| **批次生產不用盯著** | 不用每次先關瀏覽器 |

**額外的隱藏收益**：目前是**單條 16GB 跑單通道**（插槽 2 個、空 1 個）。
補一條同規格會進雙通道，記憶體頻寬翻倍——對需要在 RAM/VRAM 之間搬權重的工作
理論上有速度收益。**這是推的，這台從沒在雙通道狀態跑過。**

---

## 9️⃣ 哪些問題就算升 RAM 也不會改善？

**這題最重要，因為它決定升級後別抱錯期待。**

| 不會改善的 | 原因 |
|---|---|
| **速度抖動 0.47** | 模型層硬天花板，四種變數全試過都突破不了。跟記憶體無關 |
| **不聽動作指令** | 12 支全滅是模型行為，不是資源不足 |
| **角色漂移／黑點眉消失** | Wan 側沒有任何角色鎖定元件，這是缺元件不是缺記憶體 |
| **接龍第二段必崩** | 時序建模的限制 |
| **物理連續性（掉落、浮起、融解）** | 模型不懂物理 |
| **VRAM 8GB 的上限** | RAM 和 VRAM 是兩種資源，加 RAM 不會讓 GPU 記憶體變多 |
| **1080×1920 原生生成（若 OOM）** | 若瓶頸在 VRAM，加 RAM 無效 |

**一句話**：升 RAM 買到的是「跑得動、不會掛、能同時做更多事」，
**買不到「片子變好看」**。畫質要靠 upscale，動作要靠換模型或加控制元件。

# 第二部分：路線圖

## 現在（不需任何新下載、不需升級）

1. **修 `plan_model` 的中英文比對缺陷**（見 AUDIT 第六節）——目前守門形同虛設
2. **把 RAM 取樣移植進影片腳本**——這台的死因量不到就永遠不知道
3. **跑 B1**：1080×1920 原生能不能生（1–2 支，決定後續排序）

## 短期（低成本下載）

4. **AI Upscale**（B3）——收益確定、與模型能力無關
5. **補測 E（多角色）與 D（水）**——把兩格推論換成實測
6. **補測微笑／奸詐微笑**——頻道人設核心

## 中期（需要決策）

7. **Wan 專用 motion control** — 潛在收益最高，但要下載新模型
8. **非蒸餾版 Wan** — 每支 20–30 分鐘，量產不可行，只適合單支精修

## 升級 RAM 之後才做

9. 生圖 ＋ 生片並行的批次產線
10. 更高解析度的原生生成（前提：B1 證明瓶頸在 RAM 而非 VRAM）

---

## 三條紅線（賢賢 2026-08-16 定）

1. 不再直接修改 `pipeline.py` 的核心生成邏輯
2. 不再增加 fallback
3. 不把 Veo 接回自動產線、不刪 Wan、不宣稱新模型「已經可以」

**Benchmark 完成前，不大改 production。**
