## 一、為什麼是這個架構

### 8 GB VRAM 的核心解法：兩階段拆分

SDXL 完整管線是 UNet(5 GB) + VAE(0.3 GB) + 兩個文字編碼器(1.7 GB)。
全部塞進 8 GB 再加上訓練用的梯度與 activation，必定 OOM。

但關鍵在於：**VAE 與文字編碼器在訓練過程中，輸出永遠一樣。**
同一張圖、同一句 caption，第 1 步和第 1000 步算出來的東西完全相同——
本來就沒有理由每一步重算。

所以拆成兩支腳本：

| 階段 | 腳本 | 載入什麼 | 產出 |
|---|---|---|---|
| 1 | `01_precompute.py` | VAE + 兩個文字編碼器 | `cache_{who}/cache.pt`（2.2 MB） |
| 2 | `02_train_lora.py` | **只有 UNet** | `out_{who}/*.safetensors` |

**實測 VRAM 峰值 5.72 GB / 8 GB**，留了 2.3 GB 餘裕。

> 這跟先前 `make_depth.py` 把深度圖抽出來獨立跑，是同一個道理：
> **算出來永遠一樣的東西，就先算好存起來。**

### 分桶而不是正方形裁切

訓練圖有 448×1344 的站姿全身，也有 768×768 的臉部特寫。
如果統一置中裁成正方形，站姿那張的頭或腳會被切掉——對角色 LoRA 是致命的資訊損失。

作法：每張圖按自己的長寬比縮到總像素接近 768²，長寬各自對齊 64 的倍數。
batch size = 1，所以每張圖用自己的解析度完全沒問題。

| 圖 | 訓練解析度 |
|---|---|
| `nova_01_closeup` | 768×768 |
| `nova_02_front_fullbody` | 576×960 |
| `nova_03_front_fullbody` | 512×1216 |
| `nova_04_34standing_SIZEREF` | 448×1344 |
| `nova_05_34lying` | 704×832 |

### 只掛注意力層

`TARGETS = ["to_k", "to_q", "to_v", "to_out.0"]`

角色「長什麼樣」是被注意力層記住的。掛整個 UNet 只會讓檔案變大、
而且用 5 張圖去調更多參數，過擬合風險更高。

### 為什麼存四個 checkpoint

5 張圖訓 1000 步，很可能在中途某個點就已經最好、之後開始過擬合。
存四個才能事後挑，不用重訓。**這是拿硬碟空間換時間，很划算。**

## 三、過程中的兩個意外

### 🔴 意外一：`sd_xl_base_1.0.safetensors` 是壞的

原本計畫在 SDXL 原版上訓練（社群標準做法，LoRA 對同家族模型的通用性最好）。
載入時直接爆掉：

```
SafetensorError: Error while deserializing header:
incomplete metadata, file not fully covered
```

四個 checkpoint 逐一驗證，只有它讀不出來。**佔著 6.54 GB 但完全不能用。**

**改用 RealVisXL V5 Lightning。** 這反而可能是好事——
訓練與推論用同一個底座，LoRA 的貼合度會更好。

⚠️ **但要標記一個未驗證的風險**：Lightning 是蒸餾模型（4–8 步、低 CFG），
而訓練用的是標準 DDPM 1000 步噪聲排程，兩者的假設不完全一致。
社群有人這樣做且能用，但**我沒有實測過這台機器上的效果**。
如果 V1 結果不好，第一個要換的變數就是這個。

### 意外二：比預期快很多

原估 2–4 秒/步，實測 **1.36 秒/步**。1000 步只要約 23 分鐘。
所以把原本只訓 Nova 的計畫擴大成：Nova + Taco 兩隻都訓，還加上測試生成驗證。

### 🐛 存檔格式的 bug（已修，不需重訓）

第一次跑完，測試階段載入 LoRA 直接失敗：

```
ValueError: Invalid LoRA checkpoint.
Make sure all LoRA param names contain 'lora' substring.
```

診斷：`convert_state_dict_to_kohya()` 產出的 key 長這樣——

```
down_blocks_1_attentions_0_..._to_k.lora_down.weight   ← 少了前綴
```

kohya 格式要求所有 UNet 的 key 以 **`lora_unet_`** 開頭，ComfyUI 和 diffusers 都靠這個前綴辨識。

**關鍵判斷：權重本身是好的。** 檢查存檔內容——23,224,880 個參數、1680 個張量、
`lora_down` / `lora_up` / `alpha` 結構完整、全部非零。壞的只有命名。

所以**沒有重訓**，寫了一支改名腳本把 8 個檔案的 key 全部加上前綴，
再用 `_convert_non_diffusers_lora_to_diffusers()` 驗證能正確轉回 1120 個 diffusers key。

> 這件事的教訓：**先驗證存檔能不能被讀回來，再開始長時間訓練。**
> 如果當初第一個 checkpoint（step 250，訓練開始才 6 分鐘）就試著載入一次，
> 可以早 50 分鐘發現，而不是等整條產線跑完。
> 下次 `02_train_lora.py` 應該在存第一個檔之後立刻自我驗證。

### 另一個小坑：`ls -l` 的欄位

`ls -l` 顯示檔案只有 0.19 MB，一度以為權重沒存進去。
實際是 **家目錄 `TUF Gaming` 有空格**，把 `ls` 的欄位往後擠了一格——
`awk '{print $5}'` 讀到的是 group id（197121），不是檔案大小。
用 `stat -c%s` 確認實際是 **44.5 MB**，完全正常。

（這跟先前記錄過的「家目錄有空格會害開檔失敗」是同一個根源。）

## 八、評估結果

### ⚠️ 先更正一個我自己的誤判

第一輪測試（LoRA 權重 0.8）出來的圖全部糊掉、低對比、角色不成形，
我當下的判斷是「**V1 失敗**」。

**那個判斷是錯的。錯在我只測了一個權重。**

跑完權重掃描才發現：**LoRA 權重才是主導變數**，而 0.8 遠超過可用範圍。

### 權重掃描結果（8 步 / CFG 2.0 / 固定 seed）

| scale | 結果 |
|---|---|
| 0.00–0.15 | 黑白通用哈士奇，跟 Nova 不像 |
| 0.25 | 開始轉灰白，眼型變窄 |
| **0.35** | ⭐ **最佳**——灰白毛、細長瞇眼、得意表情，畫質銳利 |
| 0.45 | 仍可用，眼睛再窄一點 |
| 0.60 | 開始糊、眼睛快閉起來 |
| 0.80 | **完全崩壞**（第一輪測的就是這個） |

### 決定性的驗證：眼型

把生成圖跟參考圖並排（`sweep_nova/_VS_REFERENCE.jpg`），差異非常明確：

| | 眼型 | 毛色 | 表情 |
|---|---|---|---|
| 參考圖 Nova | **細長瞇眼** | 灰白 | 得意閉嘴笑 |
| scale 0.00（無 LoRA） | **又大又圓** | 黑白 | 一般 |
| **scale 0.35** | **細長瞇眼 ✓** | **灰白 ✓** | **得意笑 ✓** |

**底模型的通用哈士奇是大圓眼，Nova 是細長瞇眼。**
LoRA 把這個特徵抓到了——這是可驗證、非主觀的差異，不是「看起來好像有比較像」。

### 中途的診斷過程

原本的假設是「LoRA 打壞了 Lightning 的蒸餾特性」，所以拿更多取樣步數去測。
結果證明**假設只對了一半**：

| 設定 | 結果 |
|---|---|
| 8 步 / CFG 2 / scale 0.8 | 糊 |
| 25 步 / CFG 6 / scale 0.8 | 銳利一些，但臉扭曲 |
| 25 步 / CFG 6 / **scale 1.0** | 還是糊 |
| **8 步 / CFG 2 / scale 0.3** | **銳利又正確** ⭐ |

步數有幫助但不是關鍵，**權重才是**。所以原本的取樣設定（8 步 / CFG 2）不用改，
只要把 LoRA 權重降下來。

也順帶排除了 scheduler 不匹配的可能——實測 RealVisXL 內建與訓練用的
`prediction_type` / `beta_schedule` / `beta_start` / `beta_end` **完全一致**。

## 九之二、A/B/C/D 對照：LoRA 能不能取代 IP-Adapter？

**答案：不能，而且目前疊上去有副作用。**

### 實驗設計

同一張深度圖（`d9s1_depth_clean.png`）、同一顆 seed、同一段 prompt、同一組取樣參數，
**只改控制方式**。每張約 30 秒。

| 組別 | 雙狗構圖 | **紅酒漬**（敘事主體） | 配角像哈士奇 |
|---|---|---|---|
| **A** 只有 ControlNet | ✅ | ✅ **最完整** | ❌ 白狐狸犬 |
| **B** CN ＋ LoRA | ✅ | ❌ **消失** | ❌ |
| **C** CN ＋ IP-Adapter（現行產線） | ✅ | ✅ 很好 | ❌ 被染成棕白 |
| **D** CN ＋ IPA ＋ LoRA | ✅ | ❌ **消失** | 🟡 灰臉罩出現 |

### 發現一：構圖問題已經解決，而且不需要任何角色控制

**A 組沒有 IP-Adapter、沒有 LoRA，兩隻狗的站位依然完全正確。**
證明 8/11 的結論成立且充分：**空間資訊只要 ControlNet 深度圖就夠了。**

### 發現二：LoRA 會抹掉場景細節（新發現）

只要掛上 LoRA，紅酒漬就消失——這是 B/D 與 A/C 唯一的變數。

把權重掃一遍，得到一條乾淨的權衡曲線：

| LoRA 權重 | 紅酒漬 | 配角像哈士奇 |
|---|---|---|
| 0.00 | ✅ 完整深紅 | ❌ |
| 0.15 | 🟡 變細線 | 🟡 |
| 0.25 | ❌ 很淡 | ✅ |
| 0.35 | ❌ 幾乎全沒 | ✅ 最好 |

**根因：訓練集那 5 張圖全是「乾淨客廳裡的狗」**——沒有污漬、液體、雜亂。
LoRA 把「乾淨」當成角色特徵一起學進去了，所以它在跟 prompt 裡的酒漬打架。

這是 `DATASET_STATUS.md` 風險 4（「光線單一會被學成角色特徵」）的更廣版本，
實際發生的是**整個場景狀態**被學進去，不只是光線。

### 發現三：黑點眉在雙狗全景撐不起來

單狗測試時權重 0.35 能穩定生出兩顆黑點眉，雙狗全景四組全部沒有。
推測是狗在畫面裡佔比太低，細節解析度不夠（**未驗證**，要用局部放大或分區生成才能確認）。

## 九之三、目前的最佳作法（不用重訓就能用）

**分鏡分開用，不要一套打天下：**

| 鏡位 | 建議設定 | 理由 |
|---|---|---|
| **雙狗全景 / 有災難場景** | ControlNet ＋ IP-Adapter，**不掛 LoRA** | 敘事主體（酒漬、麵粉、岩漿）比配角品種重要得多 |

## 十、V1 沒解決的、V2 要做的

1. **可用權重區間太窄**（0.25–0.45），0.6 就開始壞。
   代表 LoRA 學得「太用力」——下次應該把 learning rate 降到 5e-5，
   或步數減到 500，讓權重可用範圍變寬、更好調。
2. **只有 5 張訓練圖，全部客廳暖窗光**。夜間、戶外的表現還沒驗證。
3. **體型差沒有專門測**——Nova 站立要是 Taco 的 3 倍，這需要兩隻同框才測得出來。
4. **底模型是蒸餾版**。`sd_xl_base_1.0` 損毀，四個本機 checkpoint 全都是蒸餾或壞的。
   要訓一版對照組，需要重新下載非蒸餾的 SDXL base（約 6.5 GB）——**這件事沒有做，等賢賢決定**。
